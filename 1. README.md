# How I Approach Solution Problems

## 01 · Discover

Understand the customer problem, business objective, operating environment, existing systems, constraints and desired outcome.

## 02 · Model

Make the problem visible through:

- Capability mapping
- Process modelling
- Customer journeys
- Actor and responsibility mapping
- Object modelling
- Service analysis
- System analysis

## 03 · Architect

Determine where responsibilities should sit across:

- Experience and workflow
- Business services
- Integration
- Information
- Systems of record
- Operational controls

## 04 · Evaluate

Consider alternative approaches across:

- Existing capability reuse
- Configuration
- Process redesign
- Automation
- Integration
- New development

Trade-offs are evaluated against customer value, operational impact, complexity, risk, maintainability and scalability.

## 05 · Prove

Where useful, reduce uncertainty through prototypes and focused proofs of concept before committing to larger implementation decisions.

## 06 · Translate to Delivery

Architecture should ultimately help teams build.

The target state therefore needs to translate into understandable:

- Requirements
- Contracts
- Data structures
- Process flows
- Integration patterns
- Decision logic
- Exceptions
- Implementation boundaries

# Architecture Principles

### Business capability before technology choice

Understand what must be achieved before deciding what should implement it.

### Reuse before duplication

Existing enterprise capabilities and services should be understood before creating new ones.

### Clear system responsibility

Every important capability, process and information object should have an understandable owner.

### Integration is an architecture concern

Cross-system behaviour should be deliberately designed rather than hidden inside interfaces or manual processes.

### Exceptions are part of the solution

A solution is incomplete if it only explains the happy path.

### Architecture must enable delivery

Architecture should create clarity for implementation rather than documentation for its own sake.

### Customer value and operational efficiency belong together

A good customer experience cannot sustainably exist on top of a broken operating model.
