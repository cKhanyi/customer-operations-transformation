Read this architecture as text
  1. A customer or banker starts or progresses onboarding.
  2. Salesforce manages the colleague workflow and case state.
  3. Salesforce sends a structured integration request to Flowgear.
  4. Flowgear validates, transforms and routes the request.
  5. Flowgear invokes reusable KYC, eligibility, document, credit and fulfilment services.
  6. Downstream systems remain authoritative owners of their business information.
  7. Flowgear returns an operational result that Salesforce can use.

E · Experience

Customer context, banker guidance, tasks and case progression.

I · Integration

Orchestration, transformation, routing, monitoring and exceptions.

S · Services

Reusable enterprise capabilities exposed through stable interfaces.

R · Systems of Record

Authoritative customer, document, credit and core data.

C# · Decision Routing

Illustrative orchestration logic 

public string RouteDecision(
    string eligibilityStatus)
{
    return eligibilityStatus switch
    {
        "APPROVED" => "CONTINUE",
        "REFER"    => "MANUAL_REVIEW",
        "STOP"     => "INELIGIBLE",
        _          => "EXCEPTION"
    };
}

Read this sequence as text
  1. The banker submits the onboarding step.
  2. Salesforce calls Flowgear.
  3. Flowgear validates and maps the request.
  4. Flowgear calls the eligibility API.
  5. Approved cases continue to credit.
  6. Referred cases create a manual-review state.
  7. Ineligible cases stop.
  8. Successful credit progression moves toward fulfilment.
Exception Architecture

Failure is part of the architecture.

    accTitle: Integration exception and recovery state model

    accDescr: The integration validates incoming requests, invokes a service and either receives a decision or handles failures. Invalid data becomes a data exception. Timeouts may retry before becoming a technical exception. Approved decisions continue, referrals move to manual review and declined decisions stop. Exceptions create operational tasks.

! · Timeout

Retry first, then expose an operational exception.

! · Invalid data

Stop malformed information before downstream execution.

! · Business exception

Refer policy or decision outcomes to an explicit route.

! · Recovery

Give operations an owner, state and next action.

Architecture Decisions

Five deliberate boundaries.

01 · Salesforce owns workflow

Case context, tasks and colleague interaction remain operational concerns.

02 · Flowgear owns orchestration

Cross-system execution is separated from the user interface.

03 · Systems retain data ownership

Middleware coordinates information without becoming another master-data store.

04 · Services are reusable

Eligibility, compliance and fulfilment are enterprise capabilities.

05 · Exceptions are explicit

Technical and business failure states have defined ownership and recovery.

01 · Receive

Accept an onboarding request through a defined API contract.

02 · Validate

Confirm required identifiers, data types and business context.

03 · Transform

Map the application into the eligibility-service contract.

04 · Invoke

Call the eligibility service and capture the response.

05 · Decide

Route approved, referred and stopped applications.

06 · Recover

Route technical failures into an explicit operational exception.

Read the POC as text
  1. Receive an onboarding API request.
  2. Validate the contract.
  3. Transform the application data.
  4. Call the eligibility service through Flowgear.
  5. Route approved, referred and stopped outcomes.
  6. Route technical failures to an exception path.
  7. Update Salesforce with the operational result.
Why This Architecture

Business value from clearer technical boundaries.

Lower coupling

Operational workflow does not depend directly on every downstream system.

Reusable capability

Services can support future journeys and channels.

Visible exceptions

Failures become traceable operational states.

Faster change

Systems can evolve behind stable integration boundaries.
