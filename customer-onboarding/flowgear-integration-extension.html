C# · Decision Routing

Illustrative orchestration logic 

public string RouteDecision(
    string eligibilityStatus)
{
    return eligibilityStatus switch
    {
        "APPROVED" => "CONTINUE",
        "REFER"    => "MANUAL_REVIEW",
        "STOP"     => "INELIGIBLE",
        _          => "EXCEPTION"
    };
}

Exception Architecture

Failure is designed — not discovered later. 

stateDiagram-v2

    [*] --> RequestReceived

    RequestReceived --> ValidateRequest

    ValidateRequest --> InvokeService : valid
    ValidateRequest --> DataException : invalid

    InvokeService --> DecisionReceived : success
    InvokeService --> Retry : timeout

    Retry --> InvokeService : retry available
    Retry --> TechnicalException : retry exhausted

    DecisionReceived --> Continue : approved
    DecisionReceived --> ManualReview : refer
    DecisionReceived --> Stop : declined

    DataException --> OperationalTask
    TechnicalException --> OperationalTask
    ManualReview --> OperationalTask

    OperationalTask --> Resolved

    Continue --> [*]
    Stop --> [*]
    Resolved --> [*]

Technical failure

Retry first, then expose an operational exception.

Invalid data

Stop malformed information before downstream execution.

Business exception

Refer policy or decision outcomes to an explicit route.

Recovery

Give operations a clear owner, state and next action.

Architecture Decisions

Five deliberate boundaries.

01 · Salesforce owns workflow

Case context, tasks and colleague interaction remain operational concerns.

02 · Flowgear owns orchestration

Cross-system execution is separated from the user interface.

03 · Systems retain data ownership

Middleware coordinates information without becoming another master-data store.

04 · Services are reusable

Eligibility, compliance and fulfilment are enterprise capabilities, not one-off integrations.

05 · Exceptions are explicit

Technical and business failure states have defined ownership and recovery paths.

01 · Receive

Accept an onboarding request through a defined API contract.

02 · Validate

Confirm required identifiers, types and business context.

03 · Transform

Map the application into the eligibility-service contract.

04 · Invoke

Call the eligibility service and capture the response.

05 · Decide

Route approved, referred and stopped applications.

06 · Recover

Route technical failures into an explicit operational exception.

Why This Architecture

Lower coupling

The operational workflow does not depend directly on every downstream system.

Reusable capability

Services can support future journeys and channels.

Visible exceptions

Failures become traceable operational states.

Faster change

Systems can evolve behind stable integration boundaries.
